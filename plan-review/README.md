# 引っ越しプランレビューから始めるスキル開発

現在作成している引っ越しプランの整合性を確認したい、という必要から始まったプロジェクトです。初版では既存の引っ越しプランのレビューに集中し、本人が求める結果を整理して、抜け漏れ・矛盾・実現可能性を確認します。

デートや旅行などへの汎用化は、引っ越しプランで実際に使い、共通して使える判断基準が分かってから進めます。

コンサルタントのような目的・ニーズの理解と、システムエンジニアのような論理的な検証を両立させます。別のレビューアによる独立レビューも組み込みます。

## 現在の段階

引っ越しプランを対象にした[SKILL.md](SKILL.md)の初稿を作成しました。スキル名は`plan-review`で、初版の対象を引っ越しに限定しています。実際の資料1件で、主担当の確認と別サブエージェントによる独立レビューを試行しました。スキルのインストールはまだ行っていません。実行用スクリプトは、必要性が確認できるまで追加しません。

## 対象とする入力

- チャットに貼り付けたプランや希望
- 単一または複数のファイル
- 資料が入ったフォルダのパス

初版の試行対象として指定されたフォルダ：

```text
C:\Users\blue_\iCloudDrive\iCloud~md~obsidian\Materus-cloud\引っ越し
```

当初は入力例として記載していましたが、ユーザーの指定を受けて確認しました。`引っ越しスケジュール（2026年11月）.md`が1件あり、これを試行対象にします。元の資料は編集せず、資料内部の整合性から確認します。

初版はテキスト・Markdownを中心に扱います。PDF、画像、表計算ファイルなどは利用可能な読取機能で確認し、確認できない資料が判断に必要なら、その制限を報告します。

## パイプライン案

```text
入力の受け取り
  → 入力の整理
  → 要件の整理
  → プランの整理・整合性チェック
  → 独立した第三者レビュー
  → 指摘の統合・プランの修正
  → 変更箇所の再確認・結果の提示
```

### 1. 入力の整理

対象資料を一覧化し、それぞれが希望、確定事項、計画、参考情報のどれに当たるかを整理します。重要な情報にはファイル名や該当箇所などの出典を残します。

- 読んだ資料と、読めなかった資料を区別する
- 重複する記載や、資料間の食い違いを抽出する
- 新しい更新日時だけを理由に、その資料を正しいと決めない
- リンク先や添付資料は、実際に確認した場合だけ確認済みとして扱う
- 大きなフォルダは資料の一覧と関連性を基に読み進め、確認範囲を明示する

### 2. 要件の整理

目的、期待する体験や結果、優先順位、避けたいこと、制約、完了条件を整理します。

情報は「明示された要望」「推測されるニーズ」「確認が必要な事項」に分けます。推測を本人の確定した希望として扱いません。質問は、回答によってプランの判断が大きく変わるものを優先します。

### 3. プランの整理・整合性チェック

行動、時間、場所、費用、準備、関係者、依存関係を必要な粒度で整理します。

共通の確認観点：

- 本人の目的・要望を実現する内容になっているか
- 必要な行動や準備に抜けがないか
- 日程、費用、移動、手順の順序が成立するか
- 資料や手順の間に矛盾がないか
- 未確認の前提に頼っていないか
- 必要に応じて、遅延や変更への対応があるか
- 段取りの細かさが、楽しさや柔軟性を損なっていないか

旅行なら移動・予約、引っ越しなら退去・入居・各種手続き、デートなら相手の希望・疲れ・過ごし方など、用途に応じた確認項目を加えます。

### 4. 独立した第三者レビュー

別のサブエージェントが、ユーザーの元の発言、対象資料またはその出典、整理した要件、プランを確認する構成を想定しています。

主担当の評価や疑っている箇所を先に渡して誘導せず、独立した観点を得ます。整理した要件が元の希望を正しく捉えているかも確認します。重要な判断は元の資料まで戻って確認します。

別のレビューアを実行できない場合は、その制限を明記し、独立レビューを実施したと報告しません。

### 5. 統合・修正・再確認

主担当がレビューの指摘を根拠と目的に照らして判断します。すべての指摘を自動的に採用するのではなく、必要な修正を行い、変更箇所とその影響を再確認します。

初版は一巡を基本とし、情報不足のまま修正とレビューを繰り返し続けない設計にします。修正案は別に提示し、元の資料の編集はユーザーから依頼された場合に行います。

## 指摘の扱い

次の区別を維持します。

| 区分 | 意味 |
| --- | --- |
| 矛盾・不整合 | 条件や記載が両立しない、または手順が成立しない |
| 抜け漏れ | 目的の達成に必要な行動・準備・条件が欠けている |
| 情報不足 | 判断に必要な情報がなく、結論を出せない |
| 改善提案 | 成立しているプランを、より目的に合う形にする提案 |

指摘には、該当箇所・根拠・影響・必要な修正または確認を付けます。別の方法を好むという理由だけで不整合と判定しません。

## 結果の提示

利用者には、次の内容を簡潔に提示する想定です。

1. 理解した目的と重要な要件
2. 確認した資料と確認できた範囲
3. 重要な指摘とその根拠
4. 修正版または修正案
5. 残る確認事項

総合判定は「整合」「修正が必要」「情報不足で判断保留」を基本案とします。「整合」は、確認できた範囲で問題が見つからなかったという意味であり、完全性の保証とはしません。

## 初回の試行（2026年10月10日）

- 対象は指定フォルダ内のMarkdown資料1件。資料内部の整合性を対象とし、リンク先の料金・制度・予約状況の最新情報は照合していません。元資料は編集していません。
- 予約や寸法確認など、すでに記載されている課題を新たな抜け漏れとして扱わず、独立レビューで区別できました。
- 追加の確認候補は、福岡到着から荷物配達までの寝床・生活用品、実家側の搬入条件です。未記載であるだけで未準備とは断定していません。
- 費用を抑える目的に対しては、運送・処分・航空便・空港移動・別送を含めた総額比較を改善案としました。
- 日程表の処分期限（11月8日）と、一部の申込項目にある「11月9日まで」の対応関係は主担当の確認候補として残します。対象品目と実際の締切を明確にすると判断しやすくなります。
- レビュー担当がさらに委任しないよう、担当範囲をSKILL.mdに追記しました。
- 形式検証用の`quick_validate.py`は、実行環境にPyYAMLがなく実行できませんでした。必須項目、名前・説明、未完了プレースホルダーは代替の構造チェックで確認しました。正式な形式検証は未完了です。

資料内部の試行であり、引っ越しの実行可能性全体を確認した結果ではありません。今後は必要な外部情報の照合と、複数資料の食い違いを含む例での動作確認を行います。
