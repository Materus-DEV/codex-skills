# 個人開発向け・仕様書作成とレビューのSkill案

現時点のアイデアをまとめたメモです。Skillの実装前に、対話を通じて内容を具体化していきます。

## 実装方針：Markdown中心の自作Skills

- GitHub Spec Kitの公式ツール一式は導入せず、工程の考え方を参考にして自作する。
- `SKILL.md`と必要なMarkdownテンプレートを中心に構成し、Codexが案件の文書を直接読み書きする。
- 仕様作成・レビューのための専用CLI、補助スクリプト、案件ごとの初期化コマンドを前提にしない。
- Skillsは一度配置して再利用し、案件ごとの仕様や決定事項は各案件のフォルダに保存する。
- Docker必須条件は、開発対象の依存関係導入・ビルド・テスト・アプリ実行に適用する。会話やMarkdownの編集にDocker実行環境は要求しない。
- Spec Kitからは、共通原則、仕様化、不明点の解消、技術設計、作業分解、整合性確認という工程の分け方を参考にする。
- 作成・設計と計画・実装と検証の3つのSkillにまとめ、各工程はSkill内のタスクとして分ける。

## 目的と利用場面

- 個人開発のアプリ・システムを対象に、Codexとの会話から仕様を整理する。
- 開発者、利用者、実行者、エラー発生時の修正担当は自分自身。
- 利用場所は自分のPC内。ほかの人への引き継ぎは想定しない。
- 長く網羅的な仕様書より、重要な判断と動作が分かる短い仕様メモを優先する。
- 詳しさは固定せず、迷いやすい点や影響が大きい点を詳しく書く。

## Skillの構成案

次の3つにまとめ、各Skill内でタスクを見出しに分ける。

1. **spec-1-doc：対話と仕様作成**
   - 共通原則（constitution）、仕様作成（specify）、不明点の解消（clarify）。
2. **spec-2-plan：設計と計画**
   - 技術構成（plan）、作業分解（tasks）、文書間の整合性レビュー（analyze）。
3. **spec-3-build：実装と検証**
   - 実装（implement）、仕様と実装の一致の確認（converge）。

各タスク後とSkill終了前にセルフチェックを実施し、項目ごとに達成・未達・対象外と根拠を記録する。必要な確認が済んでいない場合は完了とせず、次に必要な作業を残す。部分的な依頼と全工程の完了は区別する。

## 対話の方針

- 会話は短くまとめ、重要な論点を中心に進める。
- 原則として、一度に1つの論点を扱う。
- **重要な判断は相談し、細部は理由を添えて仮置きする。**
- 提案、仮定、決定事項、未決事項を区別する。
- 重要な決定の後などに、理解した内容を短く要約する。
- 質問だけを続けず、具体例や途中の草案も示す。
- 不明点が残っていても、影響しない部分は進める。
- 保存した仕様メモと必要最小限の記録から、中断後も再開できるようにする。

## 開発環境と言語：確定した共通条件

- **Dockerの利用は絶対条件とする。**
- 依存関係の導入、ビルド、テスト、アプリの実行はコンテナ内で行う。
- 案件用の言語ランタイムや開発ツールをPCへ直接導入しない。
- ソースコードや必要な成果物はPC側に保存する。
- 開発言語は固定せず、案件ごとに目的とDocker内での実行条件を踏まえて相談する。
- 言語とDocker構成は、目的・使い方を整理した後、詳細仕様へ進む前に検討する。
- データの保存先と、コンテナを作り直しても残すものを確認する。
- Dockerのイメージやボリュームの保存・削除方法も設計に含める。

「PCを汚さない」とは、開発用の依存関係をDocker内に閉じ込めることを指す。Docker自体のデータやソースコードなど、PC側に必要な保存領域は認める。

## 作成パイプラインの流れ案

1. 作りたいものと、解決したい困りごとを整理する。
2. 普段の使い方を具体例でたどる。
3. 最初に作る範囲と優先順位を整理する。
4. 開発言語とDocker構成を相談する。
5. 仕様を左右する重要な条件を確認する。
6. 決まった部分から短い仕様メモにまとめる。
7. 草案を見ながら修正し、必要に応じてレビューへ渡す。

工程は固定的な一方向ではなく、会話や草案で気づいたことに応じて前の工程へ戻れるようにする。

## 仕様メモの構成案

- **目的**：何のために作るか。
- **使い方**：どのような流れで使うか。
- **主要な動作**：何ができればよいか。
- **環境と言語**：選んだ言語、Docker構成、データの保存方針。
- **重要な条件**：制約、ファイルの上書き、失敗時に守りたいことなど。
- **未決事項**：後で決めることや、仮置きしている内容。

決定理由は、後から判断を理解するために必要なものだけ残す。

## レビューとの接続案

- 会話履歴だけに頼らず、保存した仕様メモをレビュー対象とする。
- 目的、重要な決定と理由、仮定、未決事項もレビューで参照できるようにする。
- 指摘は仕様を直接書き換える前に整理し、採用する内容を作成用Skillで反映する。
- 引き継ぎ向けの細かな管理項目は、必要性が分かってから追加する。

## 参考にする公開手法

- [英国政府のDiscovery](https://www.gov.uk/service-manual/user-research/user-research-in-discovery)：利用者の目的、現在の行動、困りごとの理解。
- [IREBの要求獲得](https://cpre.ireb.org/en/concept/requirements-elicitation)：対話や資料から要求を引き出し、誤解や衝突を解消する考え方。
- [Basecamp Shape Up](https://basecamp.com/shapeup/1.2-chapter-03)：課題と対象範囲を絞る考え方。
- [GitHub Spec Kit](https://github.com/github/spec-kit/blob/main/docs/quickstart.md)：仕様化、曖昧さの解消、品質確認を分ける構成。
- [OpenAIのSkill作成ガイド](https://developers.openai.com/plugins/build/skills)：手順とテンプレートをSkillとしてまとめる方法。

各手法をそのまま導入するのではなく、個人開発と短い対話に合う部分を取り入れる。

## 次に詰めること

- どの状態になれば「開発に進める仕様」とするか。
- 仕様メモの保存・更新方法と、再開に必要な記録。
- レビューへ移るタイミングと、確認する観点。
- 小さな題材で試す際の、使いやすさと成果物の確認方法。
