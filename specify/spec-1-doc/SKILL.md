# フェーズ1：仕様を決める

自分で開発・利用・修正するアプリについて、何を作るかを対話で決め、短い仕様書にまとめる。以下の3つのタスクを扱う。

ユーザーへの説明と進捗記録では「フェーズ1：仕様を決める」を使う。各タスクは「1-1」から「1-3」で示し、現在のタスクと次に進むタスクを短く伝える。

## 進め方と保存

- 本Skillの配置先と作業対象は別物とする。ユーザー指定の案件フォルダ、指定がなければ呼び出し時の作業フォルダを対象候補とする。以下の成果物パスは案件フォルダを基準に解釈し、Skillの配置先には案件の文書を保存しない。
- 原則1回に1つの論点を扱い、重要な判断は相談する。細部は理由付きで仮置きする。質問だけを続けず、具体例や短い草案も示す。
- ユーザーの発言、提案、仮定、決定を区別する。返答がないことを同意と扱わない。
- 指定された案件フォルダを使う。指定がなければ現在のフォルダを候補として確認し、別案件と混在する場合は保存先を質問する。
- 既存資料を確認し、既存形式を優先する。新規の場合は`docs/spec/`に`principles.md`、`spec.md`、`progress.md`を保存する。
- 初期化CLIや専用スクリプトは要求しない。Codexが直接Markdownを編集する。
- 再開時は進捗と対象文書を読み、必要なタスクから続ける。ユーザーが一部だけ指定した場合はその範囲を扱い、全工程完了とは報告しない。

## 未確認事項の記録

未回答・保留事項が生じたら[未確認事項の管理](references/questions-workflow.md)に従い、Q番号を付けてフェーズ別に記録する。回答後は合意した内容を関連文書にも反映する。

## タスク1-1：開発の基本ルールを決める

個人開発、本人による利用・修正、短い文書という前提を整理する。以下を共通原則に記録する。

- 開発対象の依存関係導入、ビルド、テスト、アプリ実行はDocker内で行う。案件用のランタイムや開発ツールをPCへ直接導入しない。
- PCとコンテナで共有するフォルダは、案件に必要な範囲に限定する。参照のみのフォルダは読み取り専用にする。
- 依存関係とキャッシュは、原則としてコンテナ内または案件専用のDockerボリュームに保存する。PC側への保存が必要な場合は、保存先と理由をユーザーに確認する。
- ソースと必要な成果物はPC側に保存できる。会話やMarkdown編集にはDockerを要求しない。
- 開発言語は案件ごとに相談する。
- 重要な判断は相談し、細部は理由付きで仮置きする。

既に合意済みの原則は毎回質問し直さない。変更を求められた場合は影響を説明し、仕様に反映する。

### セルフチェック

- 個人開発の前提とDocker必須条件が原則に記載されているか。
- 既存の合意と矛盾する原則や、未承認の重大な決定を追加していないか。

## タスク1-2：作りたいものを仕様書にまとめる

目的、本人が困る場面、典型的な利用の流れ、主要な動作、対象外、重要な条件を整理する。主要な動作には、実装後に確認できる受入条件を付ける。

仕様は短く保ち、ファイルの上書き、データ消失、外部送信など影響が大きい条件を優先する。技術選定は計画工程で相談できるよう、確定済みの制約と候補を区別する。

### セルフチェック

- 目的・使い方・主要な動作・対象範囲が読み取れるか。
- 主要な動作の成否を確認できる受入条件があるか。
- 必要な重要条件を検討し、本人の要望と異なる機能を勝手に増やしていないか。

## タスク1-3：迷う点や不明点を相談して整理する

仕様の草案から、回答によって動作、範囲、保存、実行方法が変わる不明点を優先して質問する。必要なら選択肢と違いを短く示す。回答を本文に反映し、以前の矛盾した記述を更新する。

未決事項と仮置きは仕様に残す。重要な未決事項は次工程の着手を妨げるものか明記する。細部の未決事項だけで作業全体を止めない。

### セルフチェック

- 重要な不明点が解消されているか、未決事項として影響が明記されているか。
- 決定・仮定・提案が区別され、回答を本文に反映しているか。
- 草案が元の目的と合い、古い矛盾した記述が残っていないか。

## 全体のセルフチェックと引き渡し

各タスク後と終了前に、実際の文書を読み直して上のチェックを評価する。出力しただけで完了としない。直せる不足は修正して再確認し、同じ未解決点で反復せず必要な質問を残す。

`progress.md`の本Skillの欄に、各チェック項目の「達成・未達・対象外」、根拠となる文書の見出し、未達理由または対象外理由を記録する。次に必要な作業も残す。

全体を「完了」とするのは全タスクの適用項目が達成した場合だけ。一部指定は「部分完了」、重要な回答待ちは「確認待ち」とする。非阻害の未決事項は明示したうえで残せる。Docker条件は対象外にしない。

次工程には原則・仕様・進捗を渡す。言語とDocker構成を相談する`spec-2-plan`へ進める状態を示す。依頼が仕様作成のみなら実装は開始しない。

## レビュー1への接続

作業のセルフチェック後に`spec-1-review`を案内する。作業完了とサブエージェントによるレビュー通過を区別し、未実施なら「レビュー1未実施」と記録する。レビューも依頼された場合は対応するSkillを読み、その手順で実施する。レビュー指摘の修正は、表記ミスも含めて対応を相談し、合意した範囲だけ反映する。修正後は影響範囲を再レビューする。
