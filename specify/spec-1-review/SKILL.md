# spec-1-review

`spec-1-doc`の成果物を確認する。実行時は[レビュー手順](references/review-workflow.md)を読む。レビュー担当のサブエージェントとして渡された場合も同じ手順の担当範囲に従う。

報告は[レビュー手順](references/review-workflow.md)の簡潔な形式に従う。未確認事項の採番・分類・反映状況は[未確認事項の管理](references/questions-workflow.md)で確認する。

## レビュー1の確認基準

- 基本ルール：個人開発の前提、Docker内での導入・ビルド・テスト・実行、共有を案件に必要な範囲へ限定する方針、参照だけの共有を読み取り専用にする方針が記載されている。依存関係・キャッシュは原則としてコンテナ内または案件専用のDockerボリュームで管理し、PC側への保存は理由と保存先を相談する方針がある。
- 仕様：目的、典型的な使い方、主要な動作、対象範囲、重要な条件が本人の要望と一致する。
- 受入条件：主要な動作が成功したか判断できる。
- 不明点：決定・提案・仮定・未決事項が区別され、重要な未決事項の影響が示されている。
- 悪影響：仕様内の矛盾、無断の機能追加、データ消失・外部送信などの条件漏れがない。
- 根拠：本人が選んでいない案を合意済みと扱わず、資料や会話にない事実を作っていない。
- 達成状況：作業1-1〜1-3の成果物を直接確認し、適用項目の不足、古い矛盾した記述、未反映の回答がないか評価する。進捗の「成果物作成済み」は合格の根拠にしない。

言語や技術構成は次工程で決めるため、未決という理由だけで不合格にしない。細かなUIや将来機能の未決も、主要な仕様を左右しなければ阻害事項にしない。

レビュー1では基本原則の記載を確認する。具体的な共有先、各マウントの読み書き設定、実行ユーザー・権限、Windows連携方式、ボリューム名・保存先・削除手順はレビュー2で扱い、未決であることだけをレビュー1の阻害事項にしない。ただし、既に記載された具体的な設計が本人の要望や基本原則に矛盾する場合は、レビュー1でも指摘する。

## 対象と保存先

元の要望・決定記録と、案件の`principles.md`、`spec.md`、`progress.md`を基本に確認する。既存形式を優先し、新規のレビュー結果は案件内の`docs/spec/review-1.md`へ保存する。

総合判定は「次へ進める／修正が必要／確認待ち」。次工程は`spec-2-plan`。レビュー通過を次工程の実行依頼と解釈しない。
