# フェーズ3：作って確認する

計画に沿ってアプリを作り、仕様どおりに動くか確認する。短い報告を基本にし、重要な判断は相談、細部は理由付きで仮置きする。

ユーザーへの説明と進捗記録では「フェーズ3：作って確認する」を使う。各タスクは「3-1」「3-2」で示し、現在のタスクと次に進むタスクを短く伝える。

## 入力と開始条件

本Skillの配置先と作業対象を区別する。ユーザー指定の案件フォルダを使い、未指定なら呼び出し時の作業フォルダを対象候補として確認する。別案件との混在や対象不明の場合は質問する。以下の文書パスは案件フォルダが基準であり、Skillの配置先には案件のコードや成果物を保存しない。

指定案件の原則・仕様・設計・作業一覧・レビュー・進捗と、適用されるリポジトリの指示を読む。既存形式を優先し、新規の記録は`docs/spec/`の`tasks.md`、`verification.md`、`progress.md`を使う。

実装を依頼されている範囲で進める。仕様変更やレビューのみの依頼から実装を始めない。重要な未決事項に依存する作業は回答を待ち、独立して実装できる部分は進める。

開始時にレビュー2の結果と対象を確認する。未実施・確認待ち・修正が必要、または対象が変更された場合は状態を明示し、依存する未解決の判断を勝手に確定しない。ユーザーが先行作業を明示した場合は独立して進められる範囲を扱えるが、レビューを通過したと記録しない。

## 未確認事項の記録

開始時に既存のQ番号を確認する。未回答・保留事項は[未確認事項の管理](references/questions-workflow.md)に従ってフェーズ別に記録し、回答後は合意した内容を関連文書にも反映する。

## タスク3-1：計画に沿ってアプリを作る

- 作業一覧の依存順に実装し、タスクIDと変更箇所を対応させる。
- 依存関係の導入、ビルド、テスト、アプリ実行はDocker内に限定する。ソースやMarkdownの編集はPC側で行える。
- Dockerが利用できなければ、PCへの直接導入で代替せず不足を報告する。独立した文書整理やソース編集は進められるが、実行確認済みとは扱わない。
- 保存先、上書き、外部送信などの重要な変更は相談する。小さな実装選択は理由を記録して進める。
- 機能が動くことを確認してから作業状態を更新する。未検証の作業は未検証として残す。

### セルフチェック

- 対象タスクを実装し、未実装・未検証の項目を区別したか。
- 導入・ビルド・テスト・実行をDocker内で行ったか。
- 実際のマウント設定（共有範囲と読み書きの権限）と依存関係・キャッシュの保存先が、共通原則・計画に沿っているか。
- 主要な受入条件に対応する意味のある確認を行ったか。
- 仕様と異なる重要な判断を独断で実装していないか。

## タスク3-2：仕様どおりに動くか確認する

タスクのチェック印だけを根拠にせず、仕様の主要な動作、重要な例外条件、Dockerの運用方法を実装と照合する。必要なテストや手動確認をコンテナ内で実行する。

`verification.md`に受入条件、確認方法、結果、証拠となる実行結果の要約、未検証の項目を記録する。成功・失敗・未実施を区別する。必要な場合は保存とコンテナ再作成後のデータ保持も確認する。削除手順の確認で既存のユーザーデータを削除しない。

不一致は残作業として`tasks.md`に追加または更新し、関連する仕様と結び付ける。実装に合わせて仕様を勝手に変えて合格させない。修正を依頼されている範囲なら修正して影響箇所を再検証する。検証だけの依頼なら指摘を報告する。

### セルフチェック

- 主要な受入条件を実装と照合し、実際の検証結果があるか。
- 重要な失敗時の動作やデータ保存条件を確認したか。
- Dockerによる実行方法が実装と一致するか。
- 不一致・未検証・残作業を漏れなく記録したか。

## 全体のセルフチェックと終了

各タスク後と終了前に上の各項目を評価し、`progress.md`の本Skillの欄に「達成・未達・対象外」、証拠、未達または対象外の理由、次の作業を残す。必要な検証が未実施なら完了としない。Docker条件は対象外にできない。

修正と再検証は、新しい結果に基づいて行う。同じ障害で進展がない場合は反復を止め、原因と必要な判断を報告する。

依頼範囲の適用項目が達成し、阻害する不一致がなく、必要な検証が通った場合のみ完了とする。一部の実装依頼は部分完了、判断や環境の不足は確認待ちとして示す。

終了時は実装したこと、確認結果、残作業を短く報告し、成果物へリンクする。セルフチェックを独立した第三者レビューと表現しない。

## レビュー3への接続

タスク3-2の動作確認は維持し、サブエージェントによるレビュー3とは区別する。セルフチェック後に`spec-3-review`を案内し、未実施なら「レビュー3未実施」と記録する。レビューも依頼された場合は対応するSkillの手順で実施する。レビュー指摘の修正は表記ミスも含めて相談し、合意した範囲だけ反映する。修正後は影響範囲を再レビューする。
