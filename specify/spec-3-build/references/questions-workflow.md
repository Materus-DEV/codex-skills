# 未確認事項の管理

- 未回答・保留として残す事項を、案件の`docs/spec/questions.md`へ記録する。既存の管理先があればその形式を優先する。
- 一覧は「フェーズ1：仕様」「フェーズ2：設計・計画」「フェーズ3：実装・検証」の見出しで分類する。発見した場所ではなく、決定を扱うフェーズへ置く。
- IDは案件全体で`Q-001`から連番にする。既存一覧の最大番号に1を加え、番号を変更・再利用しない。
- 登録前に同じ論点がないか確認し、既存項目は同じIDで更新する。分類を変更してもIDを維持し、複数フェーズへ重複登録しない。
- 各項目にはID、確認内容、状態、決定内容または仮置きとその理由、関連する仕様・計画・指摘の箇所、次工程への影響を記録する。
- 状態は「未確認・保留・決定済み・取り下げ」。本人の回答または確認可能な根拠なしに決定済みとしない。AIの仮置きは理由付きで未確認として残す。
- 複数エージェントを使う場合、IDの採番と一覧の更新は主担当に集約する。レビュー担当は候補を返し、同じ論点があれば既存のQ番号を使う。
- 回答後、作業用Skillでは仕様書・計画などの関連箇所へ合意した内容を反映し、一覧から該当箇所を参照する。一覧の更新だけで反映済みとしない。
- レビュー用Skillでは元の仕様・計画・コードを自動修正せず、未反映は指摘として相談する。主担当は質問一覧への登録・状態更新とレビュー結果の記録を行える。
- 会話とレビューではQ番号で参照する。会話中に解消した単純な質問をすべて登録する必要はない。
- レビュー指摘には`R1-001`・`R2-001`・`R3-001`のようにフェーズ別のIDを使い、再レビューでも既存IDを維持する。相談事項を登録した場合はQ番号で相互参照する。

各フェーズの見出しの下では、次の表を基本とする。項目がないフェーズは「なし」と記載できる。

| ID | 確認内容 | 状態 | 決定内容・仮置きの理由 | 関連箇所 | 次工程への影響 |
|---|---|---|---|---|---|

レビューでは、IDの重複、状態と根拠の一致、決定内容の文書への反映、未決事項の次工程への影響を確認する。非阻害の未決事項だけで次工程を止めない。
