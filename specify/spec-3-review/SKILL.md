# spec-3-review

`spec-3-build`の成果物を確認する。実行時は[レビュー手順](references/review-workflow.md)を読む。レビュー担当のサブエージェントとして渡された場合も同じ手順の担当範囲に従う。

報告は[レビュー手順](references/review-workflow.md)の簡潔な形式に従う。未確認事項の採番・分類・反映状況は[未確認事項の管理](references/questions-workflow.md)で確認する。

指摘の優先度・確かさ・進行への影響は、共通レビュー手順の「優先度と進行判断」に従う。

## レビュー3の確認基準

- 実装：依頼範囲の作業が実装され、仕様の主要な動作と受入条件に一致する。
- 検証：実際の確認方法・結果・対象が分かる証拠があり、失敗・未実施・成功を区別する。
- Docker：実際の導入・ビルド・テスト・実行方法、共有範囲・権限、依存関係・キャッシュの保存先が原則・計画と一致する。
- データ：重要な例外条件と保存方法、必要ならコンテナ再作成後の保持が確認されている。
- 悪影響：変更に関係する既存機能、入出力、設定との互換性、既存データへの影響を確認する。
- 根拠：チェック印や主担当の成功宣言だけで完了とせず、未実施の検証や古い実装の結果を現在の成功として扱わない。
- 残作業：不一致・未検証・未実装が漏れなく残作業へ対応し、レビュー2の阻害事項が解消されている。
- 達成状況：作業3-1〜3-2の実装・検証結果を直接確認し、重要な判断が合意した仕様から逸脱していないか評価する。作業側の実施記録だけで完了判定せず、Docker条件や受入条件は確認証拠に基づいて判断する。

必要な動作確認はDocker内で行う。Dockerが利用できない場合も静的な確認は進められるが、実動確認を達成扱いにしない。既存データや本番用ボリュームを使って破壊的な確認をしない。

## 対象と保存先

元の要望・決定記録、原則・仕様・設計・作業一覧、関連するソースと設定、`verification.md`、レビュー2、進捗を確認する。新規の結果は案件内の`docs/spec/review-3.md`へ保存する。

総合判定は「完了できる／修正が必要／確認待ち」。必要な検証証拠が不足していれば完了できると判定しない。
